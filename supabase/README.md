# Bellis development database

Supabase project: `pinfdbvfzoratsntjgah` (`sa-east-1`), created for Bellis on 27 September 2026. The SQL files in `migrations/` match the migration versions already applied to this project. Do not reapply them manually to this database.

The database currently has no professional account, tenant, patient, payment, appointment or questionnaire response data. The deployed public patient flow still uses sample data and does not send form responses to Supabase. Professional signup and `/dashboard/questionnaires` (also available at `/mis-formularios`) use Supabase Auth and store questionnaire configuration. A form group can be attached to several services in one transaction; each service has a versioned copy so historical answers remain stable.

Dynamic rules live in `questionnaire_conditions` with `question_id` (earlier source), target question, operator, value and `show`/`hide` action. A question with any `show` rules appears when at least one matches; a matching `hide` rule takes precedence. Missing or hidden source answers do not match, including `not_equals`. The versioned save RPC remaps draft question IDs to IDs in the new version. The service-role-only intake RPC recalculates visibility from saved rules, requires only visible required questions, and rejects answers for hidden questions. The table has workspace-bound foreign keys and RLS. Run `tests/dynamic_conditions_smoke.sql` in a development database to test save, required answers and hidden-answer rejection; the script rolls back all synthetic data.

Before accepting real patient responses, allowlist the Bellis `/ingresar` URL in Supabase Auth URL Configuration, implement trusted rate-limited public questionnaire read and intake endpoints around the service-role-only write RPC, test tenant isolation with separate users, provide privacy notices and retention/deletion procedures, and connect payment confirmation before enabling scheduling. Keep service-role credentials server-side only.

The security advisor currently reports only informational `rls_enabled_no_policy` findings for server-only tables. These tables intentionally have no client policies; review the [advisor guidance](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) when adding server workflows.
